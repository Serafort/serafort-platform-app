## 2026-08-30 - [Predictable Step-Up Elevation Tokens]
**Vulnerability:** `mfa.service.ts` (`stepUp.verifyTotp` / `stepUp.verifyBiometric`) minted the `elevationToken` client-side as `` `elevated-totp-${Date.now()}` `` / `` `elevated-passkey-${Date.now()}` ``. A bare timestamp is fully predictable — worse than `Math.random()` — and the value was persisted to `sessionStorage` and surfaced by `useStepUpAuth` as if it were a bearer credential. `verifyTotp` also hard-coded `success: true` and ignored the server response body.
**Learning:** A step-up/elevation token is a credential-shaped value; if the client must hold one at all it has to be issued by the server, and any client-side fallback must come from a CSPRNG and fail closed. Client-derived "proof of elevation" is UX only — the server must independently re-verify on every sensitive call. Deriving such values from `Date.now()` or `Math.random()` is never acceptable.
**Prevention:** Prefer the server-issued token (`res.data.token` / `res.data.elevationToken`) and honour `res.data.expiresAt`. Fallback is `crypto.randomUUID()` with a `crypto.getRandomValues` path, throwing if no CSPRNG exists. `verifyTotp` now derives `success` from the response. `useStepUpAuth.handleVerificationSuccess` refuses to store elevation unless `result.success && result.elevationToken`.

## 2026-08-30 - [CSPRNG for Synced-User Passwords + Idempotent-Sync Credential Reset]
**Vulnerability:** `Authentication/app/services/sync_service.ts` set every directory-synced user's password to `Math.random().toString(36).slice(-12)` via `User.updateOrCreate`. Two defects: (1) ≤52-bit, PRNG-state-recoverable value used as a credential (argon2-hashed on save, but still a targeted-guess / offline vector against every SSO account); (2) `updateOrCreate` re-ran the assignment on **every** scheduled sync, silently resetting the password of any already-provisioned user each run — an account-takeover path wherever local password login is enabled for SSO users.
**Learning:** Never use `Math.random()` for anything credential-shaped in backend code — use `node:crypto` (`crypto.randomBytes(32).toString('hex')`, matching `password_reset_controller.ts`). Separately, idempotent reconciliation jobs must not rewrite immutable-on-create fields (passwords, invite tokens) on subsequent runs; split `updateOrCreate` into `firstOrNew` + guard the create-only fields with `!row.$isPersisted`.
**Prevention:** `sync_service.ts` now uses `User.firstOrNew(...)`, assigns the profile fields every run, and sets `password = crypto.randomBytes(32).toString('hex')` only when `!user.$isPersisted`.

## 2026-08-30 - [Not A Vulnerability: request/worker correlation IDs]
**Learning:** `WorkerApiClientProxy.request()` and `api.client.ts`'s `X-Request-ID` build their id from `Math.random()`. These are local correlation keys for matching a Web Worker `postMessage` response (or a trace header) back to a pending promise — they never cross a trust boundary and gate no authn/authz decision, so `Math.random()` is acceptable there. They were still switched to `crypto.randomUUID()` (guarded, with the timestamp form as fallback) for consistency with the rest of the codebase, but this is cosmetic — do not file such IDs as security findings.
**Prevention:** When triaging a `Math.random()` hit, first establish whether the value is a credential / capability token (fix required) or a correlation/cache/render key (cosmetic at most).

## 2026-07-28 - [Secure jobId Generation]
**Vulnerability:** Weak PRNG `Math.random` used for `jobId` generation in `module-pipeline.service.ts`
**Learning:** It existed to generate a unique suffix but was not cryptographically secure, which could lead to ID predictability.
**Prevention:** Replaced with `crypto.randomUUID()`.
